Why build it

Why not just use SQLTools or Database Client?

Because the parts of Database Tools that matter day-to-day (reviewable change sets, schema-aware SQL intelligence, transaction control) don't exist in any VS Code extension. This table is the justification for building instead of settling.

Roadmap

Three phases plus a nice-to-have shelf

Each phase ends somewhere worth living in; important for a solo project, where "80% of everything" means shipping nothing.

Phase 1 · MVP

Connect, explore, query

  • Connection manager: PostgreSQL, MySQL/MariaDB, SQLite; SSH tunnel & SSL; pgpass
  • Database Explorer tree, full object depth, env colors + read-only mode
  • Query console: run statement/selection/file, object completion
  • Read-only grid: 500-row pages, count on demand, sorting
  • Core extractors (SQL inserts/updates, CSV family); run .sql files
Exit test: a normal day of database work happens in VS Code; the JetBrains icon stays in the dock, unclicked.
Phase 2 · Daily driver

Edit data, trust the SQL

  • Editable grid: change set, DML preview, submit/revert, add/delete/clone rows
  • WHERE/ORDER BY fields, header filters, FK navigation, value editor, transpose
  • Deep completion, FK JOIN inference, inspections, format, live templates
  • Tx modes + isolation, query history, output log, parameters, kill query
  • Import wizard; scripted extractors; go-to-object; view DDL
Exit test: IntelliJ muscle memory mostly works; nothing used weekly is missing.
Phase 3 · Parity

The IntelliJ feel, completed

  • Object editor dialogs (Modify Table / Column / Index); dump & restore
  • Visual explain plan + EXPLAIN ANALYZE; sessions viewer
  • Full-text search in data; find usages; rename refactor; favorites
  • Aggregate view; compare result sets; custom extractors
Exit test: nothing left that makes you reinstall IntelliJ.
Later · Nice to have: after everything else, nothing depends on these
  • ER diagrams with SVG/PNG export
  • Schema diff (live ⇄ live, live ⇄ DDL) + migration script generation
  • Additional drivers, only if a real need appears
Naming · settled

Tablecloth chosen

It goes on tables: a domestic object with a deadpan double meaning. Runner-ups (Ledger, Rolodex, Catalog) retire with honor.

Marketplace line, for later: "Tablecloth: IntelliJ-grade database tools, laid over VS Code."

Risks

What could sink it

High A clean-room rebuild, by necessity

Database Tools has no open-source counterpart to build on; it's proprietary and Ultimate-only. Tablecloth is therefore a clean-room rebuild: it uses none of JetBrains' code, and the running product serves purely as the behavioral spec.

Mitigation: replicate the UX from the product itself (its documentation and observed behavior - this plan), and build internals on open components: libpg_query (Postgres' actual parser as a library), ANTLR SQL grammars, existing SQL language servers.

High SQL intelligence is the hardest rebuild

Completion, JOIN inference, and inspections must be rebuilt from scratch; this is years of JetBrains work and the part most likely to feel shallow.

Mitigation: Phase 1 ships objects-in-schema completion only; deepen in Phase 2 on top of the open parsers rather than writing one from scratch.

Medium One-person scope

Database Tools is a full team's decade of work; chasing all of it at once means shipping none of it. The goal of "works for me" keeps the chase bounded.

Mitigation: build only checklist items actually used; each phase is a usable end-state; the nice-to-have shelf exists precisely so low-priority features can't block real ones.

Medium Grid performance on large result sets

A sluggish grid is where webview-based tools usually fall down, and where DataGrip's native grid shines.

Mitigation: adopt IntelliJ's exact model (500-row pages by default with the ⟨ 1-500 of 501+ ⟩ pager, COUNT(*) only on demand, page-size menu up to All) plus virtualized rendering within a page.

Medium IntelliJ fidelity vs. VS Code's native components

Webview surfaces (grids, consoles' result panels, dialogs) can match IntelliJ almost exactly; the explorer tree uses VS Code's native tree view, which is bound to the editor theme.

Mitigation: the genuine platform icons from intellij-community (Apache 2.0) cover most nodes, an MIT pack (Tabler / Codicons) fills DatabaseTools-only gaps, and dense tree labels recover the rest; or go full-webview for the tree at the cost of native keyboard/UX niceties.

Medium Destructive-action safety

An editable grid pointed at a real database is a foot-gun; one bad submit erodes all trust in the tool.

Mitigation: read-only mode per connection, DML preview before every submit, env colors on every surface, extra confirmation on prod-tagged sources.
